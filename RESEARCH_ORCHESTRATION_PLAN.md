## 0. Зачем всё это

Цель бота — не «ответить на вопрос», а **довести клиента до записи / заказа / передачи
менеджеру с контактом**. Сегодня мы не можем сказать цифрой, насколько хорошо он это
делает, и тем более — стало ли лучше после правки промпта или смены модели.

Все улучшения идут на ощупь: поменяли промпт → посмотрели 5 диалогов глазами → «вроде лучше».
Это потолок, и именно из-за него мы уже один раз получили регресс (после перевода на
Haiku бот стал функционально отвечать, но перестал вести к цели — так родился `funnel-rules.ts`).

**Главная метрика, которой сейчас нет в системе:**

> `% диалогов, закрытых правильно` = (запись + заказ + получен телефон и передан менеджеру) / все диалоги

Всё в этом плане служит либо тому, чтобы эту метрику считать, либо тому, чтобы её поднять.

**Принцип очерёдности: сначала приборы, потом эксперименты.**
Соблазн начать с Этапа 4 (он выглядит самым полезным) высокий. Но без Этапа 1 мы не узнаем,
помог он или навредил, и через месяц будем спорить об этом на ощущениях.

## ЭТАП 0. Диагностика потерь

**Для чего:** данные уже есть, и они могут показать, что главная потеря лежит вне этого плана.
**Риск для прода:** нулевой — только чтение.

### Шаг 0.1 — Почему телефон не сохраняется

Из 424 новых клиентов за месяц телефон есть у нуля. При этом в тексте задач видно,
что бот его **просит** («Оставьте, пожалуйста, номер телефона — тогда сразу оформим»),
то есть guard из `feedback_bot_never_escalate_without_phone` работает.

Проследить весь путь: клиент отвечает номером → парсинг (`phone-parser.ts` покрыт
тестами, значит смотреть на то, что происходит **после**) → сохранение в `Client.phone`.
Найти, где теряется.

### Шаг 0.2 — Структура 206 эскалаций

Прочитать глазами 20 эскалаций, разметить по типам: реальный клиент / входящая
партнёрка / инфлюенсер / спам / бот не справился. В выборке уже видны «предложение
о бартерном сотрудничестве» и «запрос от инфлюенсера, 36 400 подписчиков» —
это не упущенные покупатели, и в знаменателе метрики им не место.

### РЕЗУЛЬТАТ Этапа 0 (17 сентября 2026)

**Находка 1 — телефон не доходил до модели.** Бот собрал 60 номеров за 30 дней,
сохранял в `ChannelClient.phone`, тип `ChannelClientContext` его грузил — но
`buildClientContextBlock()` не выводил в текст промпта. Симметрично в TG:
`ai-memory.ts` грузил `phone` в `ClientContext` и не писал в блок «ИНФОРМАЦИЯ О КЛИЕНТЕ».

Последствие: модель каждый оборот считала, что телефона нет. Описание `create_order`
требует «ОБЯЗАТЕЛЬНО уточни телефон» → инструмент не вызывался → бот обещал передать
менеджеру → handoff-guard ловил обещание → эскалация.

**Находка 2 — заказы не создавались.** 10 эскалаций за месяц содержат уже собранный
заказ (состав + сумма, клиент подтвердил). Реально создан 1 заказ.

**Находка 3 — структура 206 эскалаций** (выборка 25):
- ~68 % реальные клиенты с намерением купить
- ~20 % блогеры / UGC-креаторы / бартер — **не клиенты**, из знаменателя метрики исключать (Этап 2.4)
- ~12 % прочее (негативные эмодзи, дубли)
- 72 из 206 (35 %) помечены `[авто-эскалация после обещания бота]` — срабатывание safety-net

**Решение владельца:** телефон для заказа обязателен всегда, полные данные собираются
всегда. Вариант «разрешить `create_order` без телефона» отклонён.

**Что сделано:** телефон выведен в промпт в обоих путях — с явной пометкой
«УЖЕ ПОЛУЧЕН, не переспрашивай» либо «НЕ ПОЛУЧЕН, обязательно попроси».
Плюс синхронизация `ChannelClient.phone` → `Client.phone`, чтобы контакт был
виден в карточке клиента в дашборде.

**Осталось:** одноразовый backfill 60 уже собранных номеров из `ChannelClient`
в `Client` — новые пишутся синхронно, старые лежат только в legacy-таблице.

## ЭТАП 1. Телеметрия оборота (`AiTurn`)

**Для чего:** появляются данные. Без этого этапа остальное измерять нечем.
**Риск для прода:** нулевой — ни один ответ клиенту не меняется.

### Шаг 1.1 — Модель `AiTurn` в Prisma

Одна строка на **оборот бота** (один входящий клиента → один исходящий, включая весь
tool-loop внутри).

```
id                String   @id @default(cuid())
businessId        String
channel           String   // telegram | instagram | whatsapp | messenger
conversationKey   String   // Conversation.id или ChannelConversation.id
clientRef         String?

model             String
complexity        String?  // simple | complex | null
salesMode         Boolean  @default(false)

tokensInput       Int      @default(0)
tokensOutput      Int      @default(0)
tokensCacheRead   Int      @default(0)
tokensCacheCreate Int      @default(0)
costUsd           Decimal? @db.Decimal(10, 6)

latencyMs         Int
iterations        Int      @default(0)
toolsCalled       String[] @default([])
recoveryUsed      Boolean  @default(false)
safetyNetFired    String?
emptyResponse     Boolean  @default(false)

createdAt         DateTime @default(now())

@@index([businessId, createdAt])
@@index([businessId, model])
@@index([conversationKey])
```

Без внешних ключей с каскадами — удаление бизнеса не должно тянуть за собой миллионы строк.

### Шаг 1.2 — Хелпер `recordAiTurn()`

Новый файл `src/lib/ai-telemetry.ts`: `createTurnTracker()` + методы `.addUsage()`,
`.addTool()`, `.markRecovery()`, `.markSafetyNet()`, `.finish()`.

`.finish()` пишет строку fire-and-forget с `.catch()`. Телеметрия не имеет права
уронить ответ клиенту.

**`trackClaudeUsage()` не трогать** — кумулятивные счётчики используются в биллинге
и в `client-cost-report.mjs`. `AiTurn` живёт рядом, не вместо.

### Шаг 1.3-1.4 — Врезка в оба пути

`src/lib/telegram/ai.ts` и `src/lib/channel-ai.ts`.

**Через `try/finally` вокруг тела функции, а не ручной `.finish()` в каждой ветке.**
Точек выхода 7 и 11 соответственно — ручная расстановка гарантированно потеряет одну,
и обнаружится это через месяц по несходящимся цифрам.

Фоновые вызовы (warmer, summaries) в `AiTurn` **не писать** — это не обороты диалога.

### Шаг 1.5 — Расчёт `costUsd`

`src/lib/ai-pricing.ts`, константа `{ model: { input, output, cacheRead, cacheWrite } }`
за миллион токенов.

> **Цены не писать по памяти.** Взять с официального прайса Anthropic (skill `claude-api`),
> проставить дату проверки комментарием.

### Шаг 1.6 — Админ-страница

`/admin/ai-turns`: фильтры по бизнесу / каналу / модели / датам. Сводка: обороты,
латентность, стоимость, % recovery, % safetyNet, распределение по моделям, топ инструментов.

**`AiTurnDaily` и cron-чистку в этот этап не включаем.** При текущем трафике 90 дней
телеметрии — порядка 20 тысяч строк, Postgres их не замечает. Вернёмся, когда объём
вырастет на порядок.

### Критерии приёмки Этапа 1

- [ ] После одного сообщения боту в TG в `AiTurn` появляется ровно одна строка с непустыми `model`, `latencyMs`, `tokensOutput`
- [ ] То же для Instagram / WhatsApp
- [ ] Диалог с `search_products` → инструмент в `toolsCalled`, `iterations >= 1`
- [ ] Искусственно сломанный вызов → клиент получает фолбэк, строка всё равно пишется с `emptyResponse = true`
- [ ] **Исключение в середине оборота → строка всё равно пишется** (проверка `try/finally`)
- [ ] `SELECT model, count(*), avg("latencyMs") FROM "AiTurn" GROUP BY model` даёт осмысленный результат
- [ ] Тесты зелёные, `wait-ci.sh` зелёный

## ЭТАП 2. Разметка исхода диалога

**Для чего:** без исхода телеметрия отвечает только на «сколько стоило», но не на «сработало ли».

### Шаг 2.1 — Достроить TG-суммаризацию

`generateConversationSummary()` в `src/lib/ai-memory.ts`: переписать промпт на JSON-выход
(`{ summary, topic, outcome }`), сохранять все три поля. Фолбэк на невалидный JSON оставить.

Дополнительных затрат нет: вызов Haiku там уже происходит.

### Шаг 2.2 — Единый словарь исходов

`src/lib/conversation-outcome.ts`:

```
booked          — запись создана
ordered         — заказ оформлен
lead_captured   — телефон получен, менеджер уведомлён
answered        — вопрос закрыт, но записи/заказа не было
escalated       — передан менеджеру
abandoned       — клиент замолчал, цели нет   ← ПОТЕРЯ
unresolved      — бот не смог помочь          ← ПОТЕРЯ
```

`booked` / `ordered` / `lead_captured` проставлять **по факту вызова инструмента**
(`create_booking`, `create_order`, `notify_manager` с телефоном), не по мнению модели.
Данные для этого есть — `toolsCalled` из Этапа 1.

Обоснование: сейчас все 71 заполненных исхода — `answered`. Модель пишет одно и то же всегда.

### Шаг 2.3 — Закрыть серую зону

**Гипотеза при составлении плана была неверной.** Предполагалось, что cron
`summarize` не разгребает очередь из-за `take: 10`. Проверка 17 сентября:
очередь пуста (`needsSummary=true` — 0 записей в обеих таблицах), cron
справляется.

Настоящая причина пустого `outcome`:

| Диалогов всего | 2554 |
|---|---|
| Короче 10 сообщений | **2473 (97 %)** — `needsSummary` не ставится никогда |
| От 10 сообщений | 81 |
| С заполненным `outcome` | 71 — **все из длинных** |

`needsSummary` выставляется каждое 10-е сообщение, поэтому 97 % диалогов
до суммаризации просто не доходят.

Шаг 2.2 (исход по факту вызова инструмента в конце оборота) закрывает это
для диалогов, где инструмент вызывался. Остаётся серая зона — диалоги
без инструментов, где исход определяется временем и последним говорящим:

- последним говорил бот, тишина > 24 ч → `abandoned`
- последним говорил клиент → `answered`

Делается в кроне одним проходом по БД, **без вызова модели** —
`outcomeFromSilence()` в `conversation-outcome.ts`.

### Шаг 2.4 — Фильтр «это вообще клиент?»

Входящая партнёрка, инфлюенсеры и спам не должны попадать в знаменатель метрики.
Критерий берётся из разметки Этапа 0.2. Без этого метрика навсегда останется низкой
и перестанет что-либо значить.

### Шаг 2.5 — Дашборд владельца

Карточка «Результаты диалогов»: за период — сколько диалогов, сколько закрыто правильно,
сколько потеряно, разбивка по каналам. Формулировки по правилу UI-копии: через пользу
для клиентов, без слов про токены и стоимость.

### Критерии приёмки Этапа 2

- [ ] У TG-диалогов заполнены `topic` и `outcome`
- [ ] `outcome = booked` проставляется только при фактическом `create_booking`
- [ ] Доля диалогов с непустым `outcome` > 90 % (сейчас 2.8 %)

- [ ] Цифры сходятся с ручной выборкой из Этапа 0.3

## ЭТАП 3. Эвалы: golden set + судья

**Для чего:** это и есть research-контур. После него любая правка промпта, смена модели
или изменение оркестрации получает ответ цифрой.

### Шаг 3.1 — Golden set

`evals/cases/*.json` — 50-80 кейсов из реальных диалогов, с маскировкой телефонов и email.

**Отбирать руками, не скриптом.** При 49 % эскалаций и потоке партнёрки автоматическая
выборка «возьми 80 последних» даст мусор.

Обязательное покрытие: цена; возражение «дорого»; торг; запись / перенос / отмена;
заказ, наличие, доставка; жалоба и негатив; не по теме и джейлбрейк; узбекский,
казахский, смешанный с русским; клиент молчит после предложения; клиент даёт
телефон / отказывается его давать.

```json
{
  "id": "price-objection-01",
  "businessFixture": "clinic",
  "history": [{ "role": "user", "content": "..." }],
  "must": { "toolsCalled": ["notify_manager"], "containsPhoneRequest": true },
  "mustNot": { "promisesDiscount": true, "escalatesWithoutPhone": true },
  "rubric": "Должен удержать клиента и предложить запись, не сбрасывая цену"
}
```

### Шаг 3.2 — Раннер

`npm run eval` → `evals/run.mjs`:

1. собирает **реальный** системный промпт через `buildSystemPrompt()` на фикстуре бизнеса
   (не упрощённую копию — иначе тестируем не то, что в проде);
2. прогоняет tool-loop в песочнице: инструменты замоканы, **в БД ничего не пишется,
   клиентам ничего не отправляется**;
3. детерминированные проверки `must` / `mustNot`;
4. LLM-судья на Sonnet по `rubric`, 0-2 балла с обоснованием;
5. отчёт: общий балл, разбивка по категориям, проваленные кейсы с диффом.

### Шаг 3.3 — Режим сравнения

`npm run eval -- --compare baseline.json`. Базовый прогон в `evals/baselines/`, коммитится.

### Правила использования

- Запускать **вручную** перед изменением промпта или модели. В CI не ставить — дорого и флаки.
- Прогон стоит десятки центов. Несопоставимо дешевле одного испорченного клиента.
- Судья тоже ошибается. Расхождения судьи и детерминированной проверки смотреть глазами.

### Критерии приёмки Этапа 3

- [ ] `npm run eval` проходит локально и печатает балл
- [ ] Ни один кейс не пишет в прод-БД и не шлёт сообщений
- [ ] Намеренная поломка промпта (убрать `funnel-rules`) → балл заметно падает.
      **Главная проверка: если не падает, эвалы бесполезны и дальше идти нельзя**
- [ ] Baseline закоммичен

## ЭТАП 3.5. Разбор монолита (оркестрация)

**Для чего:** сейчас один вызов Sonnet с 13 инструментами и промптом 15-20K одновременно
понимает намерение, ищет товар, ведёт воронку, следит за тоном, решает эскалировать
и не обещать скидку. Когда модель ошибается, непонятно, на каком из шести дел.
Промптом это лечится плохо — история с `notify_manager` и телефоном это доказала
(пришлось делать guard в коде).

**Делать строго после Этапа 3** — это самое рискованное изменение в плане, без эвалов
его катить нельзя.

### Шаг 3.5.1 — Параллелизация `(полдня, риск минимальный)`

`pickRelevantDocuments`, `pickMainModel`, `pickCacheStrategy` независимы друг от друга,
но идут последовательно. Обернуть в `Promise.all`.

Токены не меняются, минус 1-2 секунды латентности на каждом ответе.

### Шаг 3.5.2 — Deterministic-first `(2 дня, риск средний)`

Разобрать, какие tool-loop итерации — это модель, пересказывающая результат SQL.
Поиск по каталогу из 50 позиций, проверка наличия, список категорий — это код,
а не работа для LLM.

Вынести в детерминированный путь. Ожидаемо минус 30-40 % Haiku-итераций.

### Шаг 3.5.3 — Intent-роутер `(2 дня, риск выше среднего)`

Вместо одного вызова с 13 инструментами — дешёвый классификатор намерения, затем
узкий обработчик: 3-5 инструментов, промпт 5-8K.

Катить по одному бизнесу, сверяясь с эвалами после каждого шага.

### Критерии приёмки Этапа 3.5

- [ ] Балл эвалов не упал ни на одном шаге
- [ ] Средняя латентность снизилась (видно в `AiTurn`)
- [ ] Средний размер промпта уменьшился (видно по `tokensCacheCreate`)
- [ ] Доля оборотов с `iterations >= 3` снизилась

## ЭТАП 4. Состояние диалога вместо угадывания

**Для чего:** прямой удар по «бот отвечает правильно, но плавает». Сейчас модель
определяет стадию заново на каждом обороте, вчитываясь в историю — одно неудачное
сообщение, и она откатывается на «чем могу помочь».

Флоу у нас уже описан подробно (`funnel-rules.ts`, 530 строк, 7 стадий с «что делаешь /
чего не делаешь / когда переходить»). Чего нет — **исполнения этого флоу**. Разница
как между инструкцией на стене и CRM, которая не пускает дальше, пока не заполнены поля.

**Делать только после Этапов 1-3.5** — иначе эффект не измерим.

### Шаг 4.0 — Что известно о диалоге

Структурированный слепок вместо надежды, что модель вычитает из истории:

```
known: {
  intent:     string | null    // что хочет
  forWhom:    string | null
  budget:     string | null
  phone:      string | null
  objections: string[]         // что возражал
  offered:    string[]         // что уже предлагали
}
```

Хранить в `Conversation.knownFacts` / `ChannelConversation.knownFacts` (Json).

Извлекать **расширением `cart-extractor`**, а не новым вызовом модели — он уже
делает ровно это для товаров (`discussedProducts`).

Это лекарство от «плавает»: бот перестаёт переспрашивать то, что уже выяснено.
В OLLEE-аудите была ровно эта жалоба — «упоминал гидрофильное масло, потом при
уточнении забыл про него».

### Шаг 4.1 — Поле стадии

`Conversation.funnelStage` и `ChannelConversation.funnelStage` (Int 1-7, default 1)
плюс `funnelStageUpdatedAt`. Нумерация — ровно 7 стадий из `funnel-rules.ts`,
новых не выдумывать.

### Шаг 4.2 — Переходы, которые проверяет код

Условия перехода валидирует код, а не модель:

```
Стадия 2 → 3:  known.intent !== null
Стадия 5 → 6:  known.phone  !== null   ← guard про телефон становится
                                          частью модели данных, а не заплаткой
```

Механизм перехода: инструмент `advance_stage(stage, reason)` — модель сообщает
о переходе, код валидирует. Бесплатно (внутри того же вызова) и видно в `toolsCalled`.

**Escape hatch обязателен.** Клиент на стадии 2 спрашивает про доставку — бот отвечает
нормально, потом возвращается к цели стадии. Прыжки вперёд разрешены свободно
(«беру, вот телефон» на первом сообщении = законный переход 1 → 6), назад — валидируются.

### Шаг 4.3 — Промпт получает стадию, а не задачу её определить

Вместо 530 строк всех семи стадий подставлять текущую + следующую + слепок `known`:

```
ТЫ НА СТАДИИ 4 (ПРЕДЛОЖЕНИЕ). Клиент знает цену.
ИЗВЕСТНО: хочет крем от акне, для себя, возражал «дорого».
УЖЕ ПРЕДЛАГАЛИ: Крем X, Крем Y — не повторяй.
ЦЕЛЬ СЕЙЧАС — получить согласие на запись.
Стадии 1-3 пройдены. Не здоровайся повторно, не переспрашивай выясненное.
```

Побочный выигрыш: промпт короче → дешевле каждый оборот.

### Шаг 4.4 — Progress guard

`src/lib/progress-guard.ts`. Если `funnelStage` не менялась три оборота подряд,
следующий ответ строится по другой тактике: прямое предложение записи,
вопрос-закрытие либо передача менеджеру с контактом.

Логика в коде, не в промпте — промпт такие правила соблюдает нестабильно.

### Критерии приёмки Этапа 4

- [ ] `funnelStage` и `knownFacts` меняются в реальных диалогах, видно в телеметрии
- [ ] Эвалы не деградировали; кейсы «клиент молчит после предложения» и «возражение дорого» улучшились
- [ ] Средняя длина системного промпта уменьшилась
- [ ] Бот не переспрашивает то, что есть в `known` (проверить на 10 диалогах руками)

**Метрику «% закрытых правильно» за две недели не мерить** — при 424 диалогах в месяц
и одном заказе рост с 0.24 % до 0.5 % статистически неотличим от шума. Мерить по
промежуточным показателям: % диалогов, дошедших до стадии 5+; % с полученным контактом;
балл эвалов на профильных кейсах.

## ЭТАП 5. Починить обучаемость от владельца

### Шаг 5.4 — Кнопка «создать правило из инсайта» `(вынесен вперёд)`

**Ни от чего не зависит, делается в любой момент, стоит полдня.**

`insights-generator.ts` находит паттерны («бот 20 % времени отвечает "уточните
у менеджера"») и шлёт владельцу уведомление. Сейчас, чтобы это исправить, владелец
должен пойти и вручную написать FAQ или коррекцию — и поэтому не делает.

Добавить в карточку инсайта кнопку, открывающую форму создания FAQ/коррекции
с предзаполненным вопросом.

### Шаг 5.1 — Инкремент `usageCount`

Инкрементить, когда коррекция реально попала в системный промпт оборота
(fire-and-forget, батчем).

### Шаг 5.2 — Подбор по релевантности вместо «все 30»

`loadActiveCorrections()` грузит до 30 коррекций пачкой. Подбирать 5-8 релевантных
по `keywords` (поле есть в схеме, не используется). Простого совпадения по словам
достаточно, эмбеддинги на этом объёме не нужны.

Двойной выигрыш: точнее и дешевле. **Проверить эвалами**, что 5-8 релевантных
не хуже, чем 30 пачкой.

### Шаг 5.3 — Обратная связь владельцу

Коррекция, не применившаяся ни разу за 30 дней → уведомление: «правило не срабатывает,
возможно, клиенты формулируют вопрос иначе — переформулируйте».

### Критерии приёмки Этапа 5

- [ ] Кнопка «создать правило из инсайта» работает и создаёт корректную запись
- [ ] `usageCount` растёт на живых бизнесах
- [ ] В промпт попадает 5-8 коррекций вместо 30
- [ ] Эвалы не деградировали

## ЭТАП 6. Что исследовать, когда приборы готовы

Порядок по ожидаемой отдаче. Каждый пункт — отдельный эксперимент с гипотезой и метрикой.

1. **Ablation контекста.** Выключать по одному блоку системного промпта и смотреть на балл.
   Почти наверняка часть из 15-20K префикса не влияет ни на что — прямая экономия
   без потери качества, на каждом обороте навсегда.
2. **Гибрид Haiku/Sonnet.** A/B уже запущен через `AI_HYBRID_BUSINESS_IDS`, результат
   станет читаемым после Этапов 1-2. Экономит Haiku деньги или теряет их на конверсии.
3. **Судья на рискованных ответах в проде.** Только там, где бот называет цену, срок
   или скидку. Второй дешёвый вызов «это соответствует прайсу?» стоит копейки,
   одно предотвращённое ложное обещание окупает месяц.
4. **Qwen.** Превратить `qwen-offline-test.mjs` в провайдера внутри эвал-раннера.
   Решение по цифре, не по впечатлению.
5. **Лестница follow-up по стадии.** Сейчас silent-followup — одно касание через 45 минут.
   «Замолчал на цене» и «замолчал после согласия, но без телефона» — разные ситуации.

## Правила работы (не нарушать)

- Работаем **только в `main`**.
- После каждого `git push` — `bash scripts/wait-ci.sh`.
- Существующие тесты остаются зелёными. К новой логике — новые unit-тесты.
- `trackClaudeUsage`, биллинг, `client-cost-report.mjs` не трогать — новое живёт рядом.
- Любая телеметрия — fire-and-forget с `.catch()`. Упавшая аналитика не имеет права
  уронить ответ клиенту.
- Эвалы: читать prod-БД можно, писать — нельзя; телефоны и email маскировать.
- UI-копия для владельцев — через пользу для клиентов, не через токены и стоимость.

## Чего НЕ делать

- **Не начинать с Этапа 4 или 6.** Без приборов результат не измерим.
- **Не делать Этап 3.5 до эвалов.** Это самое рискованное изменение в плане.
- Не тащить эвалы в CI — дорого, недетерминированно.
- Не заменять `trackClaudeUsage` на `AiTurn` — разные задачи (биллинг vs аналитика).
- Не хардкодить цены API по памяти — только с актуального прайса, с датой проверки.
- Не раскатывать Этапы 3.5 и 4 сразу на всех: сначала 1-2 бизнеса, сравнить, потом остальные.
- **Не строить жёсткое дерево диалога.** Живые клиенты по сценарию не ходят —
  сломается на первом нестандартном сообщении. Код держит рамку, формулировки —
  за моделью.

## Порядок и ожидаемый эффект

| Этап | Что даёт | Риск для прода |
|---|---|---|
| 0. Диагностика потерь | понимание, где реально теряем; возможно ~70 рабочих лидов/мес вместо нуля | нет — только чтение |
| 1. Телеметрия `AiTurn` | данные; себестоимость на клиента; разбор всплесков расхода за минуты вместо полудня | нет |
| 2. Разметка исхода | появляется метрика цели | нет |
| 3. Эвалы | «до/после» в цифрах | нет — офлайн |
| 3.5. Разбор монолита | минус латентность, минус токены, ошибка видна на конкретном шаге | **высокий** — только под эвалами, по одному бизнесу |
| 4. Состояние диалога | бот перестаёт плавать и переспрашивать | средний — под эвалами |
| 5. Обучаемость | владелец реально учит бота | низкий |
| 6. Эксперименты | оптимизация цены и качества по приборам | зависит от эксперимента |

```
Неделя 1:  Этап 0 ──► Этап 1        (+ Этап 5.4 параллельно, независим)
Неделя 2:  Этап 2 ──► Этап 3
Неделя 3:  Этап 3.5 ──► Этап 4
Далее:     Этап 5 (остальное), Этап 6 (постоянно)
```

Этапы 0-3 не меняют ни одного ответа клиенту. Этапы 3.5-4 меняют — катятся под эвалами.

## Честная оговорка

Этапы 1-3 **не поднимут конверсию сами по себе** — это приборы, линейка, а не лекарство.
Рост дают Этапы 0, 3.5 и 4; приборы нужны, чтобы понять, дали ли они его на самом деле.

При одном активном бизнесе и 424 диалогах в месяц основную ценность даст не A/B
на живом трафике, а офлайн-прогоны на golden set — там сигнал за минуты, а не за месяцы.
